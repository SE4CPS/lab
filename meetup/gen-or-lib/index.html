Two Ways to Get a Feature

Generated code
Prompt: "date picker for a
mobile web app"

→ new file, written for this app
→ no external package added
→ not reviewed by anyone else
Existing library
npm install flatpickr

→ existing, versioned package
→ maintained outside this repo
→ transitive dependencies added
Each option changes what you own, what you test, and what you depend on. We compare both across a fixed set of aspects, then place the decision on a process model.

Speed: Time to a Working Screen

Generated
// toast.js
function toast(msg){
  const el=document.createElement('div');
  el.textContent=msg;
  el.className='toast';
  document.body.append(el);
  setTimeout(()=>el.remove(),2000);
}
Library
<script src="toastify.js"></script>
<link rel="stylesheet"
  href="toastify.css">

Toastify({text:"Saved"}).showToast();
Generated: no lookup step, code is present immediately. Library: install + read API before first use.

Maintainability

Generated
// validateForm.js
function validateForm(f){
  if(!f.email.includes('@'))return false;
  // 12 more inline rules,
  // no comments, no tests
  return true;
}
Library
const schema = yup.object({
  email: yup.string().email(),
  age: yup.number().min(18)
});
schema.validate(form);
Generated: logic lives only in this file. Library: declarative schema, documented API, shared across the codebase.

Community Coverage

Generated
function debounce(fn, ms){
  let t;
  return (...a)=>{
    clearTimeout(t);
    t=setTimeout(()=>fn(...a),ms);
  };
}
single implementation, unreviewed
Library
import { debounce } from 'lodash';

edge cases reported over years

License

Generated
Training data provenance is not
traceable per snippet.
reuse of licensed patterns from
training data cannot be ruled out
Library
package.json → "license": "MIT"
SPDX identifier, scannable in CI,
compatible/incompatible with your
project's license is checkable
Check license compatibility before adding a dependency: MIT/BSD/Apache-2.0 are generally permissive; GPL/AGPL impose copyleft obligations on distribution.

Legal

Library:     license file states terms; author/copyright
             holder is identified; most licenses disclaim
             warranty ("AS IS").

Generated:   output ownership and IP status of
             AI-generated code varies by jurisdiction and
             by the terms of the tool used to generate it.
             No warranty is typically offered either way.
Review the terms of service of the code-generation tool for IP/ownership clauses, and check your organization's policy before shipping AI-generated code in a product.

Safety: Executing Unreviewed Code

Generated
Risk: plausible-looking code
that is subtly wrong, run without
independent review.
Library
Risk: supply-chain attack —
typosquatted package name, or a
compromised maintainer account
publishing a malicious version.
Both paths need review before running in production: diff generated code like any patch; pin and audit library versions (lockfile + `npm audit` / SCA tooling).

Selection Criteria

Generate when
app-specific, one-off logic
small surface, easy to review
no security-sensitive input
exact design control needed
bundle weight matters
Use a library when
common, previously-solved problem
security or correctness critical
multiple developers touch it
long-term maintenance expected
accessibility required

Hybrid Pattern: Thin Wrapper

// generated: app-specific adapter around a library
import Flatpickr from 'flatpickr';

export function datePicker(el){
  return Flatpickr(el, {
    dateFormat:'Y-m-d',
    disable:[isPastDate]   // app rule, generated
  });
}
Security/correctness-relevant core from a library; app-specific glue as a small generated file.
